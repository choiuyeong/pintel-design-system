# Tree/List 컴포넌트 정본화 — 개발 인계용 기획문서 (관제 핵심 복합체 승격)

> **성격**: 컴포넌트 라이브러리 관제 도메인 적합성 감사에서 드러난 **"정본이 없는데 가장 많이 쓰이는 복합체 = Tree/List"** 를 정본 컴포넌트로 승격하기 위한 **개발팀 인계용 기획문서**다. 두 축을 분리해 정리한다: ① **정본화 대상·범위·기능 합집합·props 표면·anatomy·토큰 규약**(기획이 정하는 무엇을·왜·우선순위), ② **오너/디자인/개발 결정이 필요한 미확정 항목**(각 항목을 처분: 채택/보류/기각 + 차단 범위 + 근거 라인).
>
> **역할 경계(엄수)**: 기획은 '무엇을·왜·우선순위'까지다. **'어떻게 만들지'(JSX 렌더 구현·구체 코드·XAML)는 다루지 않는다** — 설계/개발 몫이라 침범하지 않는다. 본 문서는 관찰된 기능의 **합집합 정의**와 **props API 표면(이름·타입·의미)** 수준까지만 명세하고, 실제 렌더 코드는 쓰지 않는다.
> **상태**: 초안(이안). 최종 확정·정본 승격 착수는 사람/오케스트레이터가 주관한다. 본 문서는 결정을 대행하지 않고 결정 재료를 정리한다.
> **근거 원칙**: 모든 주장에 코드 사실(`파일:라인`) 또는 문서 근거를 단다. 라인은 작성 시점(2026-07-14) 직접 열람 기준(±1~2줄 가능). 확정 사실과 기획 판단/가정을 구분하고, 미확정은 `확인 필요`로 남긴다.
>
> **근거 문서(직접 열람)**:
> - `permission-settings-inline-dev-handoff.md`(권한 인계 — §4 트리 리스킨(B-5)·jsx-④ 체크박스 처분. **중복 처분 금지**: 권한 매트릭스 행 트리는 이미 처분됨 → §9에서 참조만).
> - `jsx-to-xaml-workflow.md`(JSX→XAML 워크플로 — §5 컴포넌트 매핑표. **Tree 매핑 행 부재** = §8 확인 필요로 개발 인계).
> - `design-system-adoption.md`(전역 도입 로드맵 — §3-1 3순위 Component 매핑·§5 차수. Tree/List는 2~4차 화면에 걸친 횡단 컴포넌트 → §9 정합).
>
> **정본 원천**: 화면 정본은 리포 `src/components/Library.jsx`(렌더)와 `src/data/templates.js`(문서 메타), MCP `pintel-design-system`(`get_component`/`list_templates`)이 동일 출처를 공유한다(`templates.js:1-7`).

## 1. 배경 — 감사 결론(왜 Tree/List가 1순위인가)

- **관찰(확정)**: 디자인 시스템은 원티드 Montage를 참고해 만든 것이라 관제에 안 맞는 5개 컴포넌트는 이미 컷됐고, 반대로 **관제 핵심인데 정본화가 안 된 것이 Tree/List**다.
- **사용 빈도(확정, 직접 확인)**: `templates.js`의 Library 템플릿 **총 25개 중 11개가 `uses`에 `'Tree/List'`를 선언**한다(`templates.js:37, 42, 47, 62, 67, 87, 97, 117, 122, 127, 132`). 11개 = selective-away·live·live-focus·gis-monitor·settings·stats·event-search·camera-group·event-activation·permission2·permission. → **Tree/List는 라이브러리에서 단일 최다 사용 복합체**(브리핑의 "25개 중 11개" 일치 확인).
- **정본 부재의 실체(확정)**: 컴포넌트 데이터에 `Tree.Item`(`components.js:2395`)·`Tree.Accordion`(`components.js:2429`) 엔트리가 **존재하기는 한다**. 그러나 이 둘은 Montage 계열의 **경량 메뉴 트리 문서**다 — `Tree.Item`은 hover(`#262626`)·padding indent(24/48px)·font 13px만(`:2404-2424`), `Tree.Accordion`은 grid 슬라이드 애니메이션·opacity/translateY 전환만(`:2437-2449`). **관제 실사용의 핵심(체크박스 리프·카운트 배지·카메라/분석기 리프·선택 사이드바·다계층 선택 상태)을 하나도 다루지 않는다.** → "정본이 없다"의 정확한 의미 = **문서 엔트리는 있으나 실제 관제 사용과 불일치(Montage 잔재)**. 정본화 = 관제 사용에 맞는 단일 정본으로 개정/신설.
- **증상(확정)**: 정본이 없어 **같은 트리가 최소 5곳에서 데이터 형태·기능이 제각각으로 재구현** 중(§2). 이는 일관성·유지보수·WPF 이식 비용을 모두 높인다.

> **처분 전제**: 본 문서는 감사가 정한 **Tree/List = 정본화 1순위**를 전제한다. (참고 — 2순위 Video grid: live·live-focus·unassigned·event-popup-live에서 사용 / 3순위 Toolbar: live·settings·stats·history 등에서 사용. **두 항목은 본 문서 대상 아님**, 언급만.)

## 4. Anatomy (구성요소 — 글 기술)

정본 Tree/List의 구성요소를 글로 기술한다(렌더 코드 아님).

- **행(Row)**: 트리의 최소 단위. 좌→우로 [들여쓰기 여백] · [펼침 토글 슬롯] · [체크박스 슬롯(옵션)] · [리프 아이콘 슬롯(옵션)] · [라벨] · [카운트 배지(옵션)] 의 수평 배치. 행 높이·좌우 패딩·요소 간 gap은 `SP` 토큰.
- **들여쓰기(Indent)**: depth에 비례한 좌측 여백. 관찰상 화면마다 공식이 달랐다(§2) → **정본은 단일 들여쓰기 스텝 토큰**으로 통일(값·최대 깊이는 §8 미확정).
- **펼침 토글(Expand toggle)**: 자식 보유 노드의 접힘/펼침을 나타내는 글리프. 관찰상 `▾`(펼침)·`▸`(접힘) 2-state와 항상표시 장식이 혼재. leaf에는 정렬용 spacer. 표현 방식 통일은 §8.
- **리프 타입(Leaf type)**: 노드의 종류(그룹/구역/섹션/카메라/분석기 등)를 나타내는 의미 슬롯 → 아이콘·타이포 tier 결정. kind 집합 확정은 §8.
- **카운트 배지(Count badge)**: 그룹 노드의 자식 개수 `[n]` 보조 표기(`caption2`, muted 색). 위치(라벨 내포 vs 별도 span)는 §8.
- **체크박스(Checkbox)**: leaf 선택용 13px 사각(radius 3) 체크 컨트롤. 체크 상태 표현은 관찰상 이미 수렴(선택 시 primary 채움 + 흰 체크 글리프). 그룹 노드 체크(부모-자식 전파·indeterminate·opacity)는 §8 미확정.
- **선택 상태(Selection)**: 활성 노드 배경 tint(primary 계열 저알파) + 선택적 좌측 강조바. alpha 값 통일은 §8.
- **스크롤 컨테이너**: 트리 목록을 감싸는 세로 스크롤 영역(관찰상 `overflowY:auto`). 대규모 트리 가상 스크롤 필요 여부는 §8.

## 5. props API 표면 (이름·타입·의미) — 표면까지만, 구현 아님

> **역할 경계**: 아래는 **API 표면(이름·타입·의미)** 명세다. 실제 렌더 로직·내부 상태 구현·XAML 대응은 개발 몫(다루지 않음). 이름은 권고이며 최종 명명은 설계/개발.

### 5-1. 노드 데이터 형태 (TreeNode — 합집합)

| 필드 | 타입 | 의미 | 출처 | 라벨 |
|---|---|---|---|---|
| `id`/`key` | string | 노드 식별자(선택·펼침 상태 매칭용) | E(`selTree` 라벨 매칭 개선) | 가정(권고 — 라벨 매칭보다 안정) |
| `label` | string | 표시 텍스트 | A~E | 확정 |
| `depth` 또는 `children` | number / TreeNode[] | 계층 위치(평면 depth 또는 중첩) | A~E | 확정(형태 택일은 §8) |
| `expandable` | bool | 자식 보유 → 토글 노출 | B·C | 확정(관찰) |
| `expanded` | bool | 펼침 상태 | B(`ex`)·C(`tri`) | 확정(관찰) |
| `selected` | bool | 선택 상태 | B(`sel`)·C(`sel`)·E | 확정(관찰) |
| `kind` | enum(`group`/`section`/`camera`/`analyzer`/`plain` 등) | 리프/노드 종류 → 아이콘·tier | C(`cam`)·D(`kind`)·C(`plain`) | 확정(집합 확정은 §8) |
| `count` | number \| null | 자식 개수 배지(`null`=미표기/그룹아님) | A·B·D·E | 확정(관찰) |
| `checked` | bool \| `'indeterminate'` | 체크 상태(그룹 tri-state는 §8) | C·D·E | 확정(관찰, tri-state는 미확정) |
| `disabled` | bool | 비활성(선택 불가) | (미관찰) | 가정(권고 — 접근성) |

### 5-2. 컴포넌트 props 표면

| prop | 타입 | 의미 | 책임 |
|---|---|---|---|
| `nodes`/`items` | TreeNode[] | 트리 데이터 | 화면 주입 |
| `checkable` | bool | 체크박스 모드 on/off | 화면 주입(모드) |
| `showCount` | bool | 카운트 배지 노출 | 화면 주입(모드) |
| `readOnly` | bool | 읽기 전용(A 대응) | 화면 주입(모드) |
| `selectedKey` | string | 제어형 선택 | 화면 주입(상태) |
| `onSelect(node)` | handler | 선택 변경 통지 | 화면 주입(핸들러) |
| `onToggleExpand(node)` | handler | 펼침/접힘 통지 | 화면 주입(핸들러) |
| `onToggleCheck(node)` | handler | 체크 변경 통지 | 화면 주입(핸들러) |
| `indentStep` | 토큰 | depth당 들여쓰기(내부 기본값 = 토큰) | **컴포넌트 책임**(값은 §8) |
| `iconFor(kind)` | 매핑 | kind→아이콘 슬롯 결정 | 컴포넌트 책임(집합은 §8) |

> **관찰된 안티패턴(정본에서 교정 권고, 가정)**: §2-C에서 **체크 표시가 선택 상태(`sel`)에 종속**돼 있어(`:2142-2146`) 체크와 선택이 분리되지 않는다. 정본은 `checked`와 `selected`를 **독립 필드**로 분리(D가 이미 독립 `on`). 이는 기획 판단(가정)이며 최종은 도메인 확인(§8-2).

## 6. 정본 범위 경계 — 컴포넌트 책임 vs 화면 주입

| 컴포넌트가 책임지는 것(what it owns) | 화면이 주입하는 것(what screens provide) |
|---|---|
| 행 레이아웃(들여쓰기 스텝·행 높이·gap·정렬) | 노드 데이터(라벨·depth·kind·count) |
| 깊이/kind별 타이포 tier(`TYPE`/`W`/색 토큰) | 선택·펼침·체크 **상태의 출처**(어느 노드가 선택인가) |
| 펼침 토글 글리프 표현·leaf spacer 정렬 | 상태 변경 **핸들러**(onSelect/onToggleExpand/onToggleCheck) |
| 리프 아이콘 슬롯(kind→아이콘 매핑 규칙) | 트리 구성(도메인 데이터→노드 변환) |
| 카운트 배지 위치·스타일 | 검색·필터 **로직**(무엇을 숨기고 강조할지) |
| 체크박스 시각·체크 상태 표현 | 검색어·필터 조건 값 |
| 선택 하이라이트(배경 tint + 좌측 강조바) 표현 | 대량 데이터 로딩·페이지네이션 정책 |
| hover/selected 상호작용 규약·키보드 접근성 | — |

> **경계 원칙(기획 판단)**: 컴포넌트는 **레이아웃·상태 표현·상호작용 규약**을 표준화하고, 화면은 **데이터·상태 소스·핸들러·필터 로직**을 주입한다. 검색창은 트리 상단에 함께 오지만(§2 관찰) **필터 로직 자체는 화면 책임**으로 두는 것을 권고(가정 — 최종 결합 책임은 §8-8).

## 10. 결론 — 단독 사람·오너 의존 / 확정 착수 가능 범위

**확정 착수 가능 범위(기획이 정해 인계 — 재결정 없음)**:
- Tree/List **정본화 = 1순위 채택**(§1, §8-1). 5곳 재구현(§2)을 **단일 정본으로 수렴**.
- **기능 합집합(§3)·anatomy(§4)·props 표면(§5)·책임 경계(§6)·토큰 규약(§7)** 을 개발 착수 재료로 확정 인계.
- 기존 `Tree.Item`/`Tree.Accordion`이 **Montage 잔재로 관제 사용과 불일치**함을 확인 — 정본 개정/신설 방향 채택(형태는 U-10).

**단독 사람·오너/디자인/개발 의존(착수 전 결정 필요)**:
- **디자인 결정**: U-3(카운트 위치)·U-4(선택 tint)·U-5(펼침 글리프)·U-6(kind·아이콘 집합). — 시각 규약 확정.
- **오너/도메인 결정**: U-1(최대 깊이·들여쓰기 스텝)·U-2(체크박스 그룹 규약·opacity·전파). — **U-2가 상호작용 정본의 유일한 동작 분기점**.
- **설계 결정**: U-8(검색·필터 결합 책임).
- **개발 결정**: U-9(WPF 매핑 컨트롤 — §5 매핑표 gap)·U-7(가상 스크롤, P3 비차단).
- **eval + 사람**: 정본 리스킨 결과의 시각 충실도 판정(선례 = 권한 트랙 D-5, `jsx-to-xaml-workflow.md` §7-1 S6·S7).

> 본 문서는 **무엇을·왜·우선순위**까지다. 정본 컴포넌트의 렌더 구현·XAML 매핑·토큰 키명·거처는 설계/개발, 시각 규약 확정은 디자인, 계층·체크 규약은 오너/도메인, 충실도 판정은 eval, 최종 정본 승격·착수는 사람/오케스트레이터 몫이다. 상태 = 이안(draft).
